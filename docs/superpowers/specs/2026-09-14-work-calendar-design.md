# work-calendar 설계서

작성일: 2026-09-14
상태: 사용자 검토 대기

## 1. 목적

서로 다른 회사에 속한 2~5명이 하나의 달력을 보며 "언제, 어느 회사가, 무슨 작업을 해야 하는지"를
주고받는 협업 도구. 슬랙·flow처럼 깔끔한 화면이되 기능은 최소로 한다.
핵심 동작은 두 가지다.

1. 달력의 날짜에 **작업 요청**을 올린다 (요청자 회사 → 담당 회사).
2. 담당 회사가 **완료** 버튼을 누른다.

### 하지 않는 것 (v1 범위 밖)

- 로그인, 계정, 권한 등급
- 반복 일정, 알림·이메일·푸시, 구글 캘린더 연동
- 드래그로 날짜 이동, 댓글·채팅, 파일 첨부
- 유료 인프라. 모든 구성은 무료 한도 안에서 돈다.

## 2. 접속 모델

- 호스팅: GitHub Pages. 주소 `https://ggmuhk2010-cpu.github.io/work-calendar/`
- 저장소: Firebase Firestore (Spark 무료 플랜, 하루 읽기 5만·쓰기 2만 건).
- 로그인 없음. 대신 **초대 링크에 든 비밀 키**가 열쇠다.
  - 링크 형태: `https://ggmuhk2010-cpu.github.io/work-calendar/#r=<키>`
  - 키: 소문자·숫자 24자, 브라우저의 `crypto.getRandomValues`로 생성.
  - 키는 URL 해시(`#`) 뒤에 있어 서버 로그·리퍼러에 남지 않고, 공개 저장소 코드에도 없다.
  - 키를 모르면 데이터를 읽을 수 없다. Firestore는 클라이언트에서 컬렉션 목록을 나열할 수 없으므로 키 추측 외의 경로가 없다.
- 캘린더(= room) 하나당 키 하나. 프로젝트별로 새 캘린더를 만들 수 있다.
- **신원**: 링크로 들어온 사람은 처음 한 번 "이름·회사"를 입력한다. `localStorage`에 저장되어 다음부터 묻지 않는다.
  보기는 입력 전에도 되고, 작업 요청·완료·수정·삭제는 입력 후에만 된다. 상단 칩을 눌러 언제든 바꿀 수 있다.

## 3. 화면

디자인 기준: Apple의 **iOS and iPadOS 27 UI kit**(Figma 커뮤니티 1651309003795292092)의 시각 언어를 웹으로 옮긴다.
- 색: 시스템 색(Blue #007AFF, Green #34C759, Red #FF3B30, Orange #FF9500, Purple #AF52DE, Pink #FF2D55, Teal #30B0C7, Indigo #5856D6, Yellow #FFCC00),
  배경 systemGroupedBackground #F2F2F7, 표면 #FFFFFF, 보조 라벨 rgba(60,60,67,.6), 구분선 rgba(60,60,67,.29), 채움 rgba(120,120,128,.12).
- 서체: `-apple-system, BlinkMacSystemFont, "SF Pro Text", "Apple SD Gothic Neo", Pretendard, …` (Apple 기기는 SF + Apple SD Gothic Neo, 그 외는 Pretendard). 본문 15~17px, 제목 20~22px, 큰 제목 34px.
- 형태: 캡슐(pill) 버튼·세그먼트 컨트롤·필터 칩, inset grouped 카드(모서리 20px, 행 14px), 시트형 패널·모달(모서리 28px, 모바일은 하단 시트 + 그래버).
- 재질: 상단 바와 토스트는 Liquid Glass 느낌(반투명 흰색 + backdrop blur + 얇은 하이라이트 테두리).
- 액션: 기본 액션은 시스템 블루 채움 캡슐, "완료"는 시스템 그린 채움 캡슐, 삭제는 시스템 레드 텍스트.
전화기 폭(약 400px)에서도 동작한다. 다크 모드는 v1 범위 밖.

### 3-1. 시작 화면 (키 없이 접속)

- 앱 이름 한 줄 설명 + 입력창 "캘린더 이름" + 버튼 "새 캘린더 만들기".
- 만들기를 누르면 키가 생성되고 `rooms/<키>` 문서가 만들어진 뒤 주소가 `#r=<키>`로 바뀐다.
- 곧바로 "초대 링크" 박스와 "복사" 버튼을 보여 준다. 안내: "이 링크가 있는 사람은 누구나 보고 편집할 수 있습니다."
- 안내 문구: "초대 링크를 받았다면 그 링크로 접속하세요."

### 3-2. 상단 바 (모든 화면 공통)

- 왼쪽: 캘린더 이름.
- 가운데: 탭 두 개 `달력` | `할 일`.
- 오른쪽: "초대 링크 복사" 버튼, 신원 칩(예: `홍길동 · 빅웨이브`). 칩을 누르면 이름·회사 수정.

### 3-3. 달력 탭

- 월 이동 `‹ 2026년 9월 ›` + `오늘` 버튼.
- 회사 필터 칩: 지금 불러온 작업들에서 나온 담당 회사 목록 + `전체`. 여러 개 선택 가능.
- 월 격자: 일요일 시작, 6주 × 7일. 오늘 칸 강조, 이번 달 아닌 날은 흐리게, 일요일 빨강·토요일 파랑 숫자.
- 각 날짜 칸에 작업 칩(담당 회사 색). 칩 최대 3개, 넘치면 `+N`. 완료된 칩은 회색·체크·취소선.
- 여러 날짜에 걸친 작업은 기간 안의 모든 날에 칩을 보인다(막대 연결은 하지 않는다). 첫날이 아닌 칩 앞에 `↔` 표시.
- 날짜 칸을 누르면 **날짜 패널**이 열린다. 데스크톱은 오른쪽 사이드 패널, 전화기는 아래에서 올라오는 시트.
  - 헤더: `9월 14일 (일)` + `+ 작업 요청` 버튼.
  - 그날의 작업 카드 목록. 카드: 제목, 담당 회사 태그, 담당자, 요청자(이름·회사), 마감일, 상태 배지.
  - 카드 버튼: 크게 `완료`(완료 상태면 `완료 취소`), 작게 `수정`, `삭제`. 삭제는 확인 한 번.

### 3-4. 작업 요청 폼 (모달)

| 항목 | 필수 | 규칙 |
|---|---|---|
| 제목 | 예 | 1~120자 |
| 담당 회사 | 예 | 1~40자. 기존 회사 이름이 datalist로 뜬다 |
| 담당자 | 아니오 | 0~40자 |
| 시작일 | 예 | 누른 날짜가 기본값 |
| 마감일 | 아니오 | 비우면 시작일과 같음. 시작일 이상이어야 함 |
| 메모 | 아니오 | 0~2000자 |

- 요청자 이름·회사는 신원에서 자동으로 채우고 폼에는 읽기 전용으로 보여 준다.
- 버튼: `요청 보내기` / `취소`. 수정일 때는 `저장`.
- 클라이언트 검증 실패 시 해당 칸 아래 빨간 문구. 서버 규칙 거부 시 상단 토스트 "저장하지 못했습니다".

### 3-5. 할 일 탭

- 섹션 1 `우리 회사에 온 요청`: 담당 회사 = 내 회사, 미완료. 마감일 오름차순.
- 섹션 2 `전체 미완료`: 나머지 미완료. 마감일 오름차순.
- 섹션 3 `최근 완료`: 완료된 것 중 최근 30일, 완료 시각 내림차순, 접힘 상태로 시작.
- 행: 마감일, 제목, 담당 회사 태그, 담당자, 요청자, `완료` 버튼. 마감 지난 미완료는 빨간 날짜.
- 회사 필터는 달력 탭과 공유.

### 3-6. 상태 표시

- 상단 작은 인디케이터: 오프라인이면 `오프라인` 배지. 저장 실패는 토스트.
- 저장소 연결 실패(설정 오류·규칙 거부)면 상단 배너 "저장소에 연결할 수 없습니다"를 띄우고 쓰기 버튼을 비활성화.
- 키가 있는데 `rooms/<키>` 문서가 없으면 "존재하지 않는 캘린더 링크입니다" + 새 캘린더 만들기 링크.

## 4. 데이터 모델 (Firestore)

```
rooms/{key}                      캘린더 1개
  name: string (1~60)
  createdAt: timestamp

rooms/{key}/tasks/{taskId}       작업 요청 1건 (taskId는 자동 ID)
  title:       string 1~120
  memo:        string 0~2000
  start:       'YYYY-MM-DD'
  end:         'YYYY-MM-DD'   (end >= start, 하루짜리는 start와 같음)
  toCompany:   string 1~40    담당 회사
  assignee:    string 0~40    담당자 이름
  fromName:    string 1~40    요청자 이름
  fromCompany: string 1~40    요청자 회사
  status:      'open' | 'done'
  doneAt:      timestamp | null
  doneBy:      string 0~40
  createdAt:   timestamp (서버 시각)
  updatedAt:   timestamp (서버 시각)
  updatedBy:   string 1~40
```

- 회사 색: 회사 이름 문자열 해시 → 8색 팔레트 중 하나. 별도 저장 없음.
- 쓰기는 문서 단위 last-writer-wins. 완료는 `status, doneAt, doneBy, updatedAt, updatedBy`만 갱신.
- 삭제는 실제 삭제(휴지통 없음).

## 5. 보안 규칙 (firestore.rules)

- 키 검사: `^[a-z0-9]{20,64}$` 에 맞는 경로만 읽기·쓰기 허용. 그 외는 전부 거부.
- `rooms/{key}`: 읽기·생성 허용(필드는 `name`, `createdAt`만, 길이 검사). 이름 변경 기능이 없으므로 수정·삭제 금지.
- `rooms/{key}/tasks/{taskId}`: 읽기·생성·수정·삭제 허용. 생성·수정 시 4장의 타입·길이·형식 검사,
  `status`는 두 값만, 날짜는 정규식, `updatedAt == request.time`(서버 시각 강제).
- 목적: 키를 아는 사람의 편집은 막지 않되, 잘못된 형식·거대 문서·임의 필드로 인한 오염과 남용을 막는다.
- 알려진 남용 면(결정 기록): 로그인이 없으므로 키 형식만 맞으면 누구나 새 room·문서를 만들 수 있다. 데이터 열람은 불가능하지만 무료 한도 소진(DoS)은 가능하다. v1은 이를 감수하고, 필요 시 Firebase App Check(reCAPTCHA v3, 무료)로 완화한다.

## 6. 실시간 구독 범위 (무료 한도 절약)

- 실시간 리스너 1개: `start >= (오늘 − 60일)`, `orderBy('start')`. 단일 필드 범위라 복합 인덱스 불필요.
  최근·미래 작업 전부를 덮으므로 달력 현재 달과 할 일 탭이 이 하나로 채워진다.
- 60일 넘게 과거인 달로 이동하면 그 달 범위(`start` 가 `달 시작−60일 ~ 달 끝`)를 `getDocs`로 한 번만 불러와 메모리에 합친다.
- 여러 날짜 작업의 표시 판정은 클라이언트에서 `start <= 날짜 <= end`로 한다.

## 7. 기술 구조

빌드 도구 없음. ES 모듈 브라우저 직접 로드. Firebase JS SDK는 gstatic CDN의 ES 모듈 버전.

```
work-calendar/
  index.html              뼈대 + 모듈 로드
  styles.css
  firebase-config.js      공개 웹 설정(커밋함. API 키는 공개용이며 비밀이 아님)
  firestore.rules
  firebase.json / .firebaserc
  src/
    main.js               해시 라우팅(#r=키 유무), 부트스트랩, 모듈 연결
    store.js              Firestore: room 생성·조회, 구독, 작업 생성·수정·완료·삭제
    calendar.js           순수 로직: 월 격자, 날짜 연산, 날짜별 작업 판정, 할 일 탭 그룹화
    validate.js           순수 로직: 작업 폼 검증 (규칙과 동일 기준)
    identity.js           localStorage 이름·회사
    colors.js             순수 로직: 회사 이름 → 색상
    ui/dom.js             HTML 이스케이프
    ui/toast.js           토스트
    ui/landing.js         시작 화면
    ui/topbar.js          상단 바
    ui/month.js           월 달력 + 회사 필터 + 작업 칩
    ui/panel.js           날짜 패널 + 작업 카드
    ui/list.js            할 일 탭
    ui/modals.js          신원 폼·작업 폼·초대 링크·삭제 확인
  test/
    calendar.test.mjs     node:test
    colors.test.mjs       node:test
    validate.test.mjs     node:test
    key.test.mjs          node:test
    identity.test.mjs     node:test
    rules.test.mjs        실제 Firestore 프로젝트에 Node로 접속해 규칙 허용·거부를 확인 (이 Mac에 Java가 없어 에뮬레이터는 쓰지 않음)
  .claude/launch.json    로컬 미리보기 서버
  docs/superpowers/specs/ 이 문서
```

- `calendar.js`, `validate.js`는 DOM·Firebase 의존이 없어 Node에서 그대로 테스트한다.
- `store.js`는 Firestore 호출만 감싸고 UI를 모른다. `ui.js`는 데이터를 받아 그리기만 한다. `main.js`가 둘을 잇는다.

## 8. 배포 절차

### 사장님이 직접 하는 것 (1개)

- 터미널에서 `npx firebase-tools login` 실행 후 브라우저에서 구글 계정 로그인. (OAuth 로그인은 제가 대신할 수 없음)

### 제가 하는 것

1. GitHub: `gh repo create ggmuhk2010-cpu/work-calendar --public`, 푸시, Pages 활성화(main 브랜치 루트).
2. Firebase: `firebase projects:create` → 웹 앱 등록 → `apps:sdkconfig`로 설정 추출 → Firestore DB 생성
   (`firestore:databases:create`, 안 되면 콘솔에서 "데이터베이스 만들기" 클릭 위치 안내) → `deploy --only firestore:rules`.
3. `firebase-config.js` 작성·커밋·푸시. GitHub Pages 반영(보통 1분 내) 확인.
4. 초대 링크 흐름을 실제 주소에서 검증.

### 비용

전부 무료 플랜. 결제 수단 등록 없음.

## 9. 검증 계획

1. 단위 테스트: 월 격자(윤년·6주 경계), 날짜 연산, 기간 작업 판정, 할 일 탭 그룹화·정렬, 폼 검증 전 항목.
2. 규칙 테스트: 규칙 배포 후 실제 프로젝트에 대해 Node 스크립트로 확인. 짧은 키 거부, 잘못된 status 거부, 120자 초과 제목 거부, 정상 문서 허용, room 삭제 거부. 테스트용 room은 끝나면 비운다.
3. 브라우저 검증(앱 내 브라우저): 탭 두 개로 같은 링크를 열고 A에서 요청 → B에 실시간 표시, B에서 완료 → A 반영.
   전화기 폭에서 달력·패널·폼이 깨지지 않는지. 콘솔 에러 0. 스크린샷으로 보고.
4. 실제 GitHub Pages 주소에서 새 캘린더 만들기 → 초대 링크 → 다른 브라우저 프로필로 접속까지 확인.

## 10. v1.1 확장 (2026-09-14 사용자 요청)

### 10-1. 항목 종류: 작업 요청 | 일정
- 모든 항목에 `kind`가 있다. `'request'`(작업 요청)는 기존과 같다. `'event'`(일정)는 회의·마감 같은 일반 일정이다.
- 일정: 담당 회사는 선택("관련 회사"), 완료 버튼 없음(상태는 항상 `open`), 시간(`time`, `'HH:MM'` 또는 빈 문자열) 선택 입력. 작업 요청에도 시간을 넣을 수 있다.
- 달력 칩: 시간이 있으면 `14:00 회의`처럼 시간이 앞에 붙는다. 일정 칩은 테두리형(outline)으로 작업 요청 칩과 구분한다. 회사가 없는 일정은 회색 계열.
- 할 일 탭: "우리 회사에 온 요청"과 "전체 미완료"는 작업 요청만. 새 섹션 "다가오는 일정 (30일)"에 오늘부터 30일 안의 일정을 날짜·시간순으로.
- 폼 맨 위에 세그먼트 토글 `작업 요청 | 일정`. 상단 바·날짜 패널 버튼 이름은 `+ 추가`.

### 10-2. 상세 시트 + 본문
- 카드 제목이나 할 일 행 제목을 누르면 상세 시트가 열린다. 제목, 종류·상태, 회사·담당자·요청자·기간·시간, 본문, 첨부 목록, 버튼(완료/완료 취소는 작업 요청만, 수정, 삭제, 달력에서 보기, 닫기).
- 본문은 기존 `memo` 필드를 그대로 쓰되 상한을 5,000자로 올리고 이름을 "본문"으로 바꾼다. 줄바꿈 유지(pre-wrap).

### 10-3. 첨부 (파일 + 링크)
- 저장 위치: Firestore. 파일 저장소(Storage)는 결제 수단이 필요해 쓰지 않는다.
- 항목당 첨부 최대 10개(파일·링크 합산). `tasks/{id}.attachmentCount`로 개수를 유지한다.
- 구조: `rooms/{key}/tasks/{taskId}/attachments/{attId}` = 메타(`kind: 'file'|'link'`, `name`, 파일이면 `type`·`size`·`storedSize`·`encoding`, 링크면 `url`, `uploadedBy`, `createdAt`).
  파일 내용은 `…/attachments/{attId}/blob/data` 문서의 `data`(base64 문자열)에 따로 둔다. 목록을 열 때 메타만 읽고 내용은 열기·다운로드할 때 읽는다.
- 파일은 브라우저에서 gzip 압축 후 base64로 저장(`encoding: 'gzip'`). 저장 크기 상한 700KB(716,800바이트), 원본 상한 20MB. HTML·문서류는 압축이 잘 돼 원본 수 MB까지 가능하고, 이미지·PDF는 원본 700KB 안팎이 한계다. 초과하면 "링크로 첨부하세요" 안내.
- 표시: 이미지는 시트 안에서 미리보기(열 때 내용 로드). **HTML 파일은 "열기"를 누르면 앱 안 뷰어(샌드박스 iframe, `allow-scripts`만 허용)에 렌더링**되고 "새 창에서 열기"도 된다. 그 외 파일은 다운로드. 링크는 새 탭. **유튜브 링크는 시트 안에 플레이어(youtube-nocookie 임베드)로 재생.**
- 링크는 `http://`·`https://`만 허용, 2,000자 이하, 제목 200자 이하(비우면 호스트 이름).
- 첨부는 등록·수정 폼에서 바로 붙일 수 있고(저장과 함께 업로드), 상세 시트에서도 추가·삭제할 수 있다.
- 항목 삭제 시 첨부와 내용 문서를 함께 지운다(클라이언트가 배치 삭제).
- 보안 규칙: 첨부 메타·내용 문서 모두 키가 맞는 경로만 읽기·생성·삭제 허용, 수정 금지, 필드·크기·URL 형식 검사.
- 한계(명시): 첨부 내용은 Firestore 문서라 하루 무료 읽기 5만 건·전송량 한도 안에서 쓴다. 5명 팀의 문서·사진 공유에는 충분하고, 동영상 같은 큰 파일은 링크로 붙인다.
